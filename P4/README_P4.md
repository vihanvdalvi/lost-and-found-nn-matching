# P4 data readiness handoff

This workspace prepares the Delhi Metro found-item inventory and implements component 2 of the Team G21 pipeline. It uses Python 3.10+ and the standard library.

```sh
python -m P4.prepare_data
python -m P4.candidate_filter --split dev --date 2024-03-20 --location "BRIG. HOSHIAR SINGH" --max-candidates 5
```

The first command fetches `Delhi Metro Dataset/delhimetrorail.csv` from the [LostFound collection](https://www.kaggle.com/datasets/drishyatomar/lostfound). To use a downloaded copy, run `python -m P4.prepare_data --input path/to/delhimetrorail.csv`. Generated files stay in `P4/data/` and can be regenerated by teammates. The source SHA-256 is recorded in `summary.json`.

## Parith's data handoff

| File | Contents |
|---|---|
| `data/inventory.csv` | 13,713 inventory rows with stable item IDs, text, category labels, split, and normalized receiving date/time and station |
| `category_map.json` | Ten provisional labels and the matching rules used on item names |
| `data/matching_pairs.csv` | 36 synthetic lost queries, with query date/location and one relevant found-item ID per query |
| `data/summary.json` | Source hash, row counts, data quality counts, and class distribution by split |

For the DistilBERT run described in the proposal, select rows with `text_source=description`, feed `description` as text, and use `category_id` as the target. The labels are weak labels derived from item names, with the first recognized object determining the category and `other` as the fallback. Inspect a sample from each class before training, especially multi-item names and `other`.

The original descriptions are blank in 8,208 records. For retrieval, `model_text` uses the normalized description when available and the item name otherwise. `text_source` identifies the fallback. Use the same text field, candidate pool, and development queries for both BM25 and Sentence-BERT in the primary comparison. The secondary comparison can apply the candidate filter to the same pool.

The train/dev/test split contains 9,651 / 2,034 / 2,028 inventory rows. Identical normalized model text is assigned to one split because the source lacks physical-item identifiers. This is a conservative proxy. It cannot establish whether differently worded records describe the same physical item. Two invalid quantity values were left blank. Dates and times refer to receipt of found items.

Each split has 12 labeled synthetic queries. Use `relevant_item_id` to join to `inventory.csv` and retrieve against **all** inventory rows in the same split. Keep the test split held out until final evaluation. The source supplies only found inventory, so the queries are templates built from recorded color and item type. The query date is simulated from the receiving date, and the query location reuses the receiving station. These are suitable for checking the pipeline. Results on this subset may overstate performance on real lost reports, especially when filtering by station.

## Vihan's filter handoff

```python
from P4.candidate_filter import select_candidates

candidate_ids = select_candidates(
    found_inventory,  # DictReader rows from the current split
    {2: 0.80, 0: 0.15, 9: 0.05},
    query_date="2024-03-20",
    query_location="BRIG. HOSHIAR SINGH",
    max_candidates=100,
)
```

The return value is an ordered list of item IDs. Look up their `model_text` to run the semantic matcher. Pass the classifier's full label-to-probability mapping when available. The filter combines category, date, and exact normalized station scores with provisional weights of 50%, 30%, and 20%. The date score decreases with distance over a default 14-day window and discounts a receiving date before the query date. Missing signals receive a neutral score. Lower-probability categories and other stations can still appear in the shortlist. Use the development split to tune the candidate cap, date window, and weights.
